# 工单创建幂等与聊天安全重试

## 解决什么问题

网络超时不等于业务失败。服务器可能已经创建工单，只是客户端没收到响应；重新点击发送时，如果按新请求处理，就可能再创建一张工单。

本次实现分成两层：

1. 工单层用“客户 ID + 幂等键”唯一约束保证同一次创建只保留一张工单。
2. 聊天层保存“客户 ID + 发送编号 → 原会话、原请求指纹、最终回复”，让首次会话和消息历史也能安全重试。

幂等针对同一个操作编号，不按语义相似度去重。主动发起新操作、使用新编号，仍然可以创建新工单。

## 普通工单 API

`POST /api/v1/tickets` 可携带请求头：

```http
Idempotency-Key: demo-ticket-001
```

请求体仍然只有标题、问题说明及可选订单号、会话编号。身份取自登录凭证。

| 场景 | 结果 |
| --- | --- |
| 同客户、同键、相同创建内容 | 返回同一张工单，HTTP 201 |
| 同客户、同键、不同创建内容 | HTTP 409，不创建新工单 |
| 不同客户使用同一个键 | 分别创建各自的工单 |
| 不提供键 | 保留旧行为，每次成功请求创建新工单 |

键长度为 1–128，只能包含英文字母、数字及 `._:-`。`chat-operation:`、`agent-run:` 前缀由后端保留，外部接口拒绝使用。

指纹来自 Pydantic 验证后的完整创建内容：字段按固定顺序转为 JSON，再计算 SHA-256。原有指纹算法没有改变，已有记录仍能复用。

先查再插入只能减少冲突，不能避免并发重复；最终保证来自数据库唯一约束。遇到指定唯一约束冲突时，先回滚失败事务，再读取获胜记录并核对指纹。其他数据库错误继续向上抛出。

## 普通聊天、SSE 与图片问答

文本接口 `POST /api/v1/chat`、`POST /api/v1/chat/stream` 增加可选字段：

```json
{
  "message": "请创建人工服务工单，协助排查耳机连接问题。",
  "conversation_id": null,
  "client_request_id": "564b240e-9ecb-4d4a-a07e-1c222901d870"
}
```

图片接口 `POST /api/v1/images/upload` 在 form-data 中使用同名字段 `client_request_id`。

- 一次新的发送生成一个 UUID，重试保留原 UUID、原消息和原始 `conversation_id`。
- 首次请求使用 `conversation_id: null`，重试仍使用 null；不要改成响应中的会话编号。
- 同一编号可以在普通聊天与 SSE 之间重试，传输方式不参与指纹。
- 图片指纹使用原始图片字节的 SHA-256，不使用可能变化的视觉模型输出。换了图片字节就是不同内容，会返回 409。
- 编号按登录客户隔离。同客户同编号变更输入会在模型调用前返回 HTTP 409。
- 已完成请求回放原回复与原会话，不再次调用 Agent、不追加重复聊天消息。SSE 回放为一个 token 事件和一个 done 事件。
- 原操作仍在处理时，普通接口返回 409；SSE 已建立时发送 error 事件。稍后用原请求重试。
- 不提供发送编号仍兼容旧接口，但不保证跨 HTTP 请求重试去重。

### 为什么需要 chat_operations 表

如果只把幂等键放在工具参数中，首次聊天重试仍可能创建新会话；模型也可能重新改写标题和描述，使工具参数指纹变化。

现在原始输入先落库，首次会话和发送记录在同一事务中创建。并发竞争中落败的事务连同新会话一起回滚。后端从发送记录 ID 派生工具幂等键，逐层传递到 Agent 工具执行器；模型不能指定客户身份、会话或这个键。

聊天仍使用已有的会话租约和 fencing token：生成前取得处理权，保存前锁定并校验处理权。最终的用户消息、助手消息和发送完成结果在同一事务中提交。

### 提交后失败如何恢复

```text
客户端发送稳定编号
  → 复用/创建发送记录及会话
  → 获取会话处理权
  → 已完成：回放结果
  → 未完成但已有对应工单：从工单恢复回执
  → 尚无工单：执行 Agent
  → 原子保存两条聊天消息与完成结果
```

工单可能已经独立提交，而后续聊天事务失败。重试会先按工具幂等键查询已提交工单，恢复真实回执，不再次执行模型建单。图片观察结果也会保存在发送记录中，重试复用。

同一次发送内重复的建单工具调用也共用一个键：相同参数返回已有工单，不同参数返回明确冲突，不会新建第二张。

## Vue 如何配合

`frontend/src/api/chatIdentity.ts` 将登录凭证、原会话、正文和图片字节摘要组合计算本地标识，只在 sessionStorage 中保存“哈希 → UUID”，不保存正文、凭证或图片。

- 发送失败后，相同输入再次发送复用编号；切换普通/SSE 不改变编号。
- 同一标签页刷新后，只要仍使用原登录凭证和原始输入，可以复用未确认发送的编号。
- 成功后清理该编号，并读取服务端历史，替换本地失败/临时气泡。
- 点击“新聊天”表示主动开始新操作。重新登录、清空存储、关闭标签页后不保证找回原编号。
- 浏览器禁用 sessionStorage 时，退回当前页面内存；不做自动重发。

## 数据库迁移与边界

迁移顺序：`37614203d392 → c8c1fafea0b1 → a61e7f3b902d`。前者补齐工单键/指纹与约束，后者新增聊天发送记录。原业务库和专用测试库均已升级到后者，并通过 Alembic check；没有修改 .env。

- 已完成聊天回放的是当时保存的回复，可能含历史状态；查询最新工单状态要调用详情接口。
- 新增工单回复尚未接入请求级幂等，重复成功回复仍会增加消息。
- 单次发送最多创建一张工单；多工具混合调用的其他写入不构成一个原子事务，也没有通用工作流恢复。
- 工单回执恢复不会自动继续其他业务工具；它只确认已提交的工单。
- 未实现发送记录的自动清理、跨标签页编号同步或重新登录后的发送恢复。
- 客户端未收到响应的故障通过注入异常/模拟 fetch 验证，未执行操作系统强制断电或真实代理断网实验；这也不是吞吐量压测。
